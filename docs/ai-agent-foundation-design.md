# 岩崎AIエージェント「土台」設計案 v0.1

作成日: 2026-09-11 / 状態: **岩崎の合意待ち**（合意前に作り込みはしない）

---

## 0. 結論

- **AI会社の正体は「岩崎1人 ＋ 役職ごとのAIエージェント5体 ＋ 共通の土台」**。土台とは、①会社の憲法（方針・禁止事項）②会社知識（商材・価格・トーク）③正データ（顧客・案件・活動・請求）④承認ルール⑤ツール接続、の5つ。
- **技術は「Claude Code ＋ このリポジトリ ＋ 既存コネクタ」で始める（案A）**。独自アプリ開発（案B）は後回し。理由は、稼働が岩崎1人で、いま使っている環境に freee / Gmail / Google カレンダー / Google ドライブ / Notion / Slack が既に接続されているため。
- **顧客への送信・請求・契約・支払いは全てAIの「下書き」止まり。実行は岩崎が承認**。ここは信用と法令に直結するので、最初から固定する。
- 着手順は **土台 → 事務 → インサイドセールス → 経理 → 経営幹部 → アウトサイドセールス**。効果が早く、失敗しても信用を傷つけない順。

## 3. 全体アーキテクチャ（5層）

```
┌──────────────────────────────────────────────────────┐
│ L4 入口   岩崎 ⇄ Claude Code（1本のチャット）            │
│           ＋ 定期実行（朝の指示出し・週次レビュー）       │
├──────────────────────────────────────────────────────┤
│ L3 役職   経営幹部 / インサイド営業 / アウトサイド営業 /  │
│           経理 / 事務   （各1ファイルで定義）             │
├──────────────────────────────────────────────────────┤
│ L2 承認   自動OK / 岩崎承認 / 禁止 の3段（§5）           │
├──────────────────────────────────────────────────────┤
│ L1 知識   憲法・商材・価格・ICP・トーク・競合・書式        │
│           （リポジトリ内 company/ に平文で置く）          │
├──────────────────────────────────────────────────────┤
│ L0 データ 顧客・案件・活動・見積・請求                     │
│           正はスプレッドシート（仮）、会計の正は freee     │
└──────────────────────────────────────────────────────┘
      接続: Gmail / カレンダー / ドライブ / Notion / Slack / freee
```

設計原則

1. **正データは1か所**。顧客・案件はスプレッドシート（仮）、会計は freee。AIは両方を読むが、書き込みは承認付き。
2. **知識は平文ファイル**。岩崎が直接読める・直せる。AIの品質＝この平文の品質。
3. **役職＝ファイル1枚**。「目的・担当業務・使ってよいツール・承認境界・成果指標」を書く。人を雇うときの職務記述書と同じ。
4. **全ての外向き行動はログを残す**。誰に何を送ったか、後から追える。

## 4. 役職エージェント定義（案）

### 4-1. 経営幹部（COO役）
- 目的: 岩崎の「今日何をやるか」を決める材料を出す。
- 担当: 週次KPIレビュー、パイプライン停滞の指摘、優先順位提案、他エージェントの成果チェック。
- 入力: 案件シート、活動ログ、日報、freee の売上・入金。
- 出力: 月曜朝の「今週の一手」、金曜の「今週の数字と来週の改善」。
- ツール: 読み取りのみ（シート・freee・カレンダー）。
- 承認境界: 提案まで。判断は岩崎。
- 指標: 提案の採用率（岩崎が「採用/不採用」を1タップで残す）。

### 4-2. インサイドセールス
- 目的: 会わずに進む工程（リスト化・初回接触文面・追客）を回す。
- 担当: ターゲットリスト整備、業種別DM/メール文面の作成、返信の要約と次アクション提案、追客リマインド、アポ候補日の提示。
- 入力: 顧客シート、Gmail（受信）、トーク台本、DMテンプレ。
- 出力: 送信「下書き」（Gmail 下書き作成まで）、追客リスト、返信要約。
- ツール: Gmail（下書き作成・受信の読み取り）、カレンダー（空き確認）、シート。
- 承認境界: **送信は岩崎**。値引き・条件変更の文面は作らない。
- 指標: 下書き→送信率、返信率、アポ数。

### 4-3. アウトサイドセールス（訪問支援）
- 目的: 訪問の前後を軽くする。
- 担当: 当日の訪問先リストとルート案、訪問先ごとの直前メモ（前回接触・決裁者・反論対応）、訪問後の音声/一言メモから活動ログ作成と次アクション登録。
- 入力: 顧客シート、カレンダー、トーク台本、競合表。
- 出力: 朝の「訪問パック」、夜の活動ログ・日報下書き。
- ツール: シート、カレンダー。
- 承認境界: 提案まで。見積は数値を勝手に決めず、価格表から引く。
- 指標: 日報記入にかかる時間の短縮（現状値は未計測＝仮置き）。

### 4-4. 経理
- 目的: 請求・入金・経費の漏れをゼロにする。
- 担当: 成約→請求書下書き作成、入金消込の照合、未入金の督促文面作成、月次の売上・粗利集計、経費の勘定科目案。
- 入力: 案件シート、freee（取引先・請求書・入金）。
- 出力: 請求書「下書き」、未入金一覧、月次サマリ。
- ツール: freee（読み取り＋下書き作成）、Gmail（督促文の下書き）。
- 承認境界: **freee への確定登録・送付は岩崎**。税務判断は論点整理まで、最終確認は税理士。
- 指標: 請求漏れ件数、督促までの日数。

### 4-5. 事務
- 目的: 岩崎の手が止まる雑務を先回りする。
- 担当: スケジュール調整の文面、契約書・見積書のひな形からの差し込み、書類のドライブ整理、取引先マスタの整備、期限リマインド（更新・支払・許認可）。
- 入力: 取引先マスタ、ドライブのひな形、カレンダー。
- 出力: 書類下書き、リマインド、整理済みフォルダ。
- ツール: ドライブ、カレンダー、Notion または シート、Slack（自分宛て通知）。
- 承認境界: 契約書の条文変更は提案まで。捺印・送付は岩崎。
- 指標: リマインド漏れ件数。

## 5. 承認マトリクス（土台の中核）

| 行為 | 自動OK | 岩崎承認 | 禁止 |
|---|:-:|:-:|:-:|
| リスト作成・要約・集計・文面下書き | ○ | | |
| Gmail 下書き作成 | ○ | | |
| Gmail **送信**、LINE/DM送信 | | ○ | |
| カレンダー予定の作成 | | ○（自分だけの予定は自動OK可） | |
| 見積書・請求書の下書き | ○ | | |
| 見積書・請求書の**発行・送付** | | ○ | |
| freee への取引・請求の確定登録 | | ○ | |
| 支払い・振込 | | | ○（AIは触らない） |
| 値引き・契約条件の判断 | | | ○（岩崎のみ） |
| 法的・税務的な断定表現を顧客へ出す | | | ○ |
| 顧客の個人情報を社外サービスへ転記 | | ○（必要最小限） | |
| 実在企業名・統計値の推測記載 | | | ○（出典なしは書かない） |

運用ルール: AIは承認が必要な行為を「下書き＋理由＋リスク」の形で提示し、岩崎が「承認/修正/却下」を返す。この履歴が学習用ログになる。

## 6. データモデル（正データの置き場）

正データは Google スプレッドシート1冊（仮置き。質問11-2で確定）。シート単位で以下。

| シート | 主キー | 主な列 |
|---|---|---|
| 取引先 | 取引先ID | 名称、業種、住所、緯度経度、決裁者、電話、メール、LINE、紹介元、ステージ、優先度、担当メモ、反社チェック日 |
| 案件 | 案件ID | 取引先ID、商材（清掃/フィルター/燃料）、ステージ、金額（月額/単発）、確度、次アクション、期限、失注理由 |
| 活動 | 活動ID | 日時、取引先ID、チャネル、結果、メモ、次アクション、記録者（岩崎/AI） |
| 見積 | 見積ID | 案件ID、明細、金額、有効期限、承認状態 |
| 請求 | 請求ID | 案件ID、freee請求書ID、金額、発行日、入金日、状態 |
| 日報 | 日付 | 既存列のまま |
| 価格表 | 商材コード | 単価、原価、条件（AIはここからしか価格を引かない） |

ステージ・チャネル・業種の定義は現行アプリのものを流用（未接触/初回接触/提案済/交渉中/成約/失注）。

## 7. 技術選定

| | 案A: Claude Code ＋ リポジトリ ＋ コネクタ（推奨） | 案B: 独自Webアプリ（CORLY OS拡張＋API） |
|---|---|---|
| 初期工数 | 小（ファイル整備が中心） | 大（認証・サーバー・UI） |
| 岩崎の操作 | Claude のチャットに話しかける | スマホ画面 |
| 自動実行 | 定期実行（Routine）で朝夕の指示出しが可能 | 自前で組む |
| リスク | Claude 環境依存 | 開発・保守が岩崎1人に乗る |
| 判断 | **まずこれ** | 案Aで型が固まってから、必要な画面だけ移植 |

案Aの具体: このリポジトリに `company/`（知識）と `.claude/agents/`（役職）を置き、Claude Code から役職を呼び出す。コネクタ経由で Gmail・freee 等を操作。

## 10. リスクと回避策

| リスク | 内容 | 回避策 |
|---|---|---|
| 個人情報保護法 | 顧客の氏名・連絡先をAIサービスへ渡す | 渡すのは業務上必要な最小限。利用目的は「営業・契約管理」の範囲内。AI事業者側のデータ保持条件を確認し、必要なら社内規程に明記。最終確認は専門家へ |
| 特定電子メール法 | 営業メール/DMの一斉送信 | 送信者名・住所・受信拒否方法を文面に固定で入れる（テンプレ側で担保）。一斉送信は行わず1通ずつ承認。最終確認は専門家へ |
| 信用毀損 | AIが価格・実績・法的表現を誤って書く | 価格は価格表のみ参照、実績は実績シートのみ、法的断定は禁止（§5）。送信前に岩崎承認 |
| 会計誤登録 | freee に誤った取引が入る | 下書き止まり。確定は岩崎。月次で税理士確認 |
| 燃料販売仲介の許認可 | 仲介の形態によって必要な登録・資格が変わる可能性 | **論点整理まで**。現行の契約形態を質問11-1で確認し、専門家へ |
| 反社チェック | 新規取引先の与信 | 取引先シートに「反社チェック日」列を必須化。未実施なら経理エージェントが契約前に警告 |
| 1人依存 | 岩崎が見なければ何も動かない | 「承認待ち」を毎朝1回 Slack/メールに集約。1日1回見れば回る設計 |
| 環境依存 | Claude 環境が止まる | 知識・データは平文とスプレッドシートに残るので、AIなしでも業務は継続できる |

## 11. 確認したい質問（回答をもらってから段階0を作る）

1. **燃料販売仲介**: 誰から誰へ、何を、どの契約形態で仲介しているか。清掃と同じ営業フローに乗せるか、別扱いか。
2. **正データの置き場**: Google スプレッドシート / Notion / freee の取引先マスタ、のどれを「顧客・案件の正」にするか。（推奨: スプレッドシート。既に日報連携があり、freee は会計に専念させる）
3. **freee の利用実態**: 会計・請求書・人事労務のうち、どれを実際に使っているか。請求書は freee で発行しているか。
4. **日常の入口**: Claude Code（この画面）/ Claude アプリ（スマホ）/ CORLY OS（Web）のどれで毎日操作したいか。
5. **AIの権限**: §5 の承認マトリクスで「自動OK」を広げたい行為はあるか（例: 自分だけの予定登録、Slack 自分宛て通知）。
6. **目標数値**: アプリ内の「フィルター175枚」「訪問15件/日」等は実績目標か、サンプル値か。
7. **顧客データの現物**: 現在の顧客リストはどこにあるか（紙 / Excel / スマホ連絡先 / 頭の中）。件数の目安。
8. **通知先**: 承認待ちの集約は Slack か Gmail か LINE か。
9. **費用感**: AI利用料と工数にかけられる上限（月額の目安と、週に使える時間）。

## 12. 用語

- **正データ**: 唯一の正しい記録。コピーが複数あるとき、必ずこちらを信じる。
- **承認境界**: AIが自分で実行してよい範囲と、岩崎の承認が要る範囲の線引き。
- **役職エージェント**: 職務記述書を持ったAI。人の役職と同じ粒度で責任範囲を切る。
