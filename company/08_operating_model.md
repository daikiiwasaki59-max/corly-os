# 08 AIの置き方（全体最適）

決定: 2026-09-14。岩崎の指示「全体的な設計としてはこうしたい」（全体最適の型）を、1人の会社に翻訳したもの。

## 結論
**中心に置くのは AI ではない。AI が読み書きする「正データ ＋ 会社知識」が中心で、AI はそれを扱う手。**
中心が空なら、AI を何体並べても部分最適にしかならない。いまスプレッドシート「CORLY OS」が未作成なので、**中心は空のまま**。ここを埋めるのが最初の一手。

## 部分最適と全体最適の違い
| | 部分最適 | 全体最適 |
|---|---|---|
| 形 | 業務ごとに AI を使う。業務同士はつながらない | 全ての業務が同じ正データと会社知識を読み書きする |
| 例 | メールの下書きだけ AI、リスト作成だけ AI | 取引先シート1枚を、営業も経理も事務も見る |
| 得られるもの | 岩崎の作業が少し速くなるだけ | 横断が見える。知識が残る |

## 3つの利いてくる順（記事の順と逆にする）
1人の会社では「部署をまたぐ重複」は存在しない。順番を入れ替える。

### 1位: 知識の財産化
- いま、会社の中身は **ほぼ全部が岩崎の頭の中**。書き出さないと、休めない・任せられない・引き継げない。
- 仕組み: 訪問 → 一言メモ → 活動ログ（AI が記録）→ 有効だった返しを AI が候補として提示 → **岩崎が「採用」と言ったものだけ** `03_playbook.md` に昇格。
- これが溜まると、リポジトリ自体が資産になる。人を雇うとき、庄栄興産に引き継ぐとき、渡すのはこれ。

### 2位: 属人化の解消
- 岩崎が倒れたら全部止まる。大槻は現場、岩崎は営業と経営で、重なりがない。
- 仕組み: 価格は価格表からしか引かない。文面はテンプレから。承認は承認待ちシートで。
- 目標は「岩崎に聞かないと分からない」をゼロに近づけること。

### 3位: 全体の効率化
- 部署がないので重複業務はない。代わりにあるのは **同じ相手への機会損失**。
- 中心にデータがあると、次が見える。
  | 見えるもの | 例 |
  |---|---|
  | 同じ会社が2つのリストにいる | 管理会社が自社で車両を持っていれば、燃料も提案できる |
  | 取引先が別の役割も持つ | 協力工務店は工事の発注先であり、燃料（重機）の候補でもある |
  | 1回の訪問で2つ提案できる | 清掃の納品先で、燃料の話を1分する |
- 業務ごとに別々に AI を使っていると、これは見つからない。

## 中心の中身（3層）
| 層 | 中身 | 場所 |
|---|---|---|
| 正データ | 取引先・案件・活動・見積・請求・承認待ち・日報 | スプレッドシート「CORLY OS」（**未作成**）と freee |
| 会社知識 | 憲法・商材と価格表・ICP・プレイブック・文面・承認ルール | このリポジトリ `company/` |
| 役職エージェント | exec / inside-sales / outside-sales / accounting / admin | `.claude/agents/` |

接続: Gmail / カレンダー / ドライブ / freee / LINE。

## 運用のルール
1. **正データは1か所**。同じ情報を2か所に書かない。
2. **役職エージェントは同じデータを見る**。役職ごとに別のリストを作らない（清掃と原状回復で管理会社リストを分けないのと同じ理由）。
3. **岩崎が話したことは必ずどこかに落ちる**。落ちなかった情報は、無かったことになる。
4. **AI が勝手に知識を書き換えない**。プレイブックへの昇格は岩崎の「採用」が要る。
5. **月1回、横断で見る**。exec が「2つのリストに同じ会社がいないか」「取引先が別の役割を持てないか」を報告する。
